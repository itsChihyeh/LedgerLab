# P5 验收清单

2026-11-02。P5 = 商户提现：双门槛受理（商户可用和 `free_cash`）、模拟银行出站付款、结果未知时不释放资金、查询恢复、银行确认拒绝才失败、出账后退回、银行流水匹配、提现侧对账与老化，以及第五种受限纠错（已判失败的提现其实已出账）。范围见 [phases.md](../design/phases.md)，设计正本是 [ADR-0006 的 2026-11-02 补充](../adr/0006-payout-unknown-outcome.md) 和 [ADR-0011 第 8 节](../adr/0011-restricted-correction.md)。

做法同 P3/P4：Claude Code 先补设计（新增 AC-6.15、AC-7.22～7.27），拆成 12 个小任务（T01–T11，审查中插入 T04b）；Codex 在本机实现、只跑相关测试、本地提交；本机执行者独立跑一遍全量 verify 全绿才推到 `p5`；Claude 在云端看 diff、抽查复跑。每个提交正文带 `Task: Txx`。Codex 停下提问 3 次：T02（出站命令 `request_id` 全局唯一和查询命令冲突 → 改成两个部分唯一索引）、T07 两问（能否在 `ledger` 枚举里加纠错类型 → 可以；纠错后的银行余额断言 → 并入 T08）。从开工到全部推送约 10.5 小时，开工前基线在 `main` 上全绿（1556/0）。

## 1. 合并方式

一个 PR：`p5` → `main`，基于当前 `main`（`d6740b7`），不叠加。合并这一个就完成 P5。

## 2. 自己验收（前提：JDK 25、Node 24、Docker 在运行）

```sh
./mvnw verify                              # 主应用：1800 个测试，全部跑在真 PostgreSQL 上
./mvnw -f simulator/pom.xml verify         # 模拟器：154 个（新增银行出站付款接口）
cd frontend && npm ci && npm run check && npm run test:e2e   # 前端单测 32 个；Playwright 7 组 12 个
sh scripts/smoke-p5.sh                     # 三进程冒烟：正常提现、丢回执恢复、银行拒绝、出账后退回，最后三段对账
sh scripts/smoke-p4.sh && sh scripts/smoke-p2.sh   # 旧冒烟仍然通过（CI 里四个都跑）
```

smoke-p5 成功时：四条路径各自 PASS；三段对账 FINISHED，0 发现、0 OPEN 差异；最后现金与商户可用各 4680 分，其他账户为 0；不变量通过，对账没有改账。

可选：`./mvnw -Pmodel test -Dtest=PaymentModelProperties` 跑随机序列（现已加入提现受理、银行回执四种、出账、退回、冲突出账、纠错⑤、运营查询），报告在 `target/model-report.md`。

## 4. 值得看一眼的地方

1. **两个新迁移**。V21：`core.payout`、`core.payout_status_history`（只追加），银行行加 `matched_payout_id` 和 `PAYOUT_PAID`/`PAYOUT_RETURNED` 状态，纠错类型加 `CONFIRM_FAILED_PAYOUT_PAID`；出站命令的 `request_id` 从全局唯一改成两个部分唯一索引（提交类永久唯一，查询类只对未完成的唯一）。V22：给 readonly 的提现命令/尝试脱敏摘要视图（不在 T04 列出的范围里，我审查后接受：符合“readonly 看 io 只走脱敏视图”的口径）。模拟器 V6：`sim_bank.outgoing_payment`。已提交的迁移没有改动。
2. **新模块** `payouts`（依赖 ledger、outbound、refunds、reconciliation 的公开入口）。银行导入按 `reference` 前缀分流：`po_` 走批次、`mpo_` 走提现、入账流水号走 P4 的待查收款退还，互不干扰。
3. **现金只认银行流水**：银行 API 说 EXECUTED 或 RETURNED 都只把提现推进到 ACCEPTED（T04b 修的就是 RETURNED 曾经让命令一直重试），出账和退回分录只由流水触发。
4. **冲突证据**（银行先说拒绝、后来又出账）不自动处理，开 `PAYOUT_STATE_CONFLICT`，由运营走纠错⑤。纠错后商户可用可以变负（显示商户欠款），现金不能为负（数据库拒绝 → 409）。
5. **对账规则版本**升到 `p5-v1`；按旧证据时点重跑的报告不变。
6. 运营查询接口 `POST /api/payouts/{id}/query` 和纠错接口一样，公开演示配置不注册。
7. CI 冒烟加跑 smoke-p5。设计文档里几处“留后续任务”的旧措辞已补注已实现。

## 5. 替你定下、可以推翻的取舍

- 模拟银行的 `TIMEOUT` 故障直接回 504，不真的挂起到客户端超时：对我们来说同样是“结果不明”，测试快很多。
- 银行 API 只能把提现推进到 ACCEPTED；ACCEPTED 之后银行主动取消（不经查询）首版不处理，靠 1 个工作日老化报警加运营查询。
- 不做部分提现、取消已受理提现、提现手续费、即时到账、多收款账户。
