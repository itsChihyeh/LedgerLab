## 4. 值得看一眼的地方

### 4.1 采纳为什么只开放两种原因

采纳不是“把结论变成动作”，而是“打开一张已有写接口的预填表单”。所以只有在系统里**已经有对应写操作**、且结论的引用足以填满那张表单的原因才开放：`BANK_SPLIT_DEPOSIT` → 待查收款归位（`APPLY_UNAPPLIED_CASH`，ADR-0011），`PROCESSOR_FEE_DIFFERS` → 接受差异。其余 11 种原因没有可用的系统写操作（等下一份对账单、向银行调单、联系处理方、升级等都是线下动作；`WEBHOOK_LOST` 的处理是补投事件，不是纠错），面板只显示“没有可采纳的系统操作，请按建议线下处理”。前端用一个封闭映射表加单元测试（`ac_11_4 only SPLIT and FEE are adoptable among the 13 causes`）钉死：以后有人加了第三种，测试会提醒要同时过设计和 ADR。预填必须能从引用里**唯一**推出（一个批次、至少两条银行流水），推不出就不显示采纳。

### 4.2 结论为什么存在调查服务一侧

主应用不知道 Agent 的存在：没有新表、没有迁移、没有新路由，也不调用 Python。结论是调查服务自己的追加 JSONL，不是账本，可以整个删掉。好处是 P9 对资金路径和数据库权限零改动，Agent 的输出不可能混进账务数据。代价是追溯要两边对：采纳后主应用的纠错 `reason_note`（或差异状态历史的说明）以 `采纳调查 inv_…` 开头，用这个 `runId` 去 JSONL 里能找回完整记录（模型、工具调用、引用核验）。JSONL 被删后，主应用里的备注还在，但看不到完整调查过程。

### 4.3 零写权限分哪几层落地

模型被注入后最坏能做什么，取决于下面几层各自独立成立（前三层沿用 P8，见 [p8.md](p8.md) 4.1，后几层是 P9 新增）：

1. **P8 工具层**：固定工具表、参数正则校验、固定模板的 GET、不跟随重定向。
2. **服务端路由测试**（AC-10.2）和 **`readonly` 数据库角色**（ADR-0014）：同一份 `routes.json`，处理器只碰只读数据源。
3. **服务包和 MCP 包的静态检查**（AC-11.2、AC-11.8）：只导入标准库、`ledgerlab_agent` 和自身，没有出站 HTTP、socket、shell、数据库；调查服务唯一的写是追加自己的 JSONL。MCP 包与核心包的检查完全相同，没有例外。两个包放在核心包外面，是因为评测的代码指纹覆盖整个核心包，往里加文件会让评测多写日志行。
4. **调查服务的入口**：只监听回环、校验 `Host`、只认 JSON POST、不回 CORS 头（别的网站借不了用户的浏览器）、一次只跑一个、模型启动时固定为不花钱的替身或基线。
5. **前端的人工关口**：写只发生在浏览器到主应用这一条路上，由人填操作人并点“提交”，请求由前端按封闭映射组装，后端按 ADR-0011 全部重新校验（流水 reference、金额合计、批次状态……）。被注入的模型最坏只能给出一个错误的预填，过不了后端校验就不会写入，过得了的也必须有人点。

### 4.4 MCP 为什么不用 SDK、不实现 2026-07-28 无状态模式

- **不用 SDK**：官方 `mcp` 包是新的运行时依赖，AGENTS.md 铁律 5 要先问；而这里只需要 `initialize`、`ping`、`tools/list`、`tools/call` 四个方法，标准库几百行就够，也便于对协议行为写确定性测试。
- **不实现无状态模式**：2026-07-28 版规范的无状态模式（每个请求带 `_meta` 版本、`server/discover`）还太新，生态里的客户端支持不一，实现它会增加协议面而不增加功能。按该版规范，同时支持两个时代的客户端在服务端只支持旧版时会改用 `initialize` 连接，所以只支持 `2025-11-25`、`2025-06-18`、`2025-03-26` 的初始化式握手不会把这些客户端挡在外面。这是个可以以后加的扩展，不是已有设计的缺口。
- 不提供 `investigate`、resources、prompts、sampling：MCP 客户端自己的模型做推理，服务端只给证据，所以也不存在“MCP 服务调用大模型而花钱”的路径。

## 6. 已知限制

- **替身不代表大模型**：面板和记录里的结论来自规则基线经模型接口的替身，界面固定标“本地替身（规则基线），不代表大模型能力”。看到“采纳”能用，说明管道通了，不说明任何大模型能做对账调查。评测的局限见 [p8.md](p8.md) 第 6 节。
- **调查服务是单进程、同步、一次一个**：第二个请求立即 409，不排队；一次调查在界面上要等它跑完（替身只要几毫秒，真实后端上是几次 HTTP 往返）。
- **记录在本机文件里**：JSONL 在运行调查服务的机器上，没有备份、没有多机共享、不是账本；换机器或删文件就看不到历史调查。
- **生产构建不带调查服务**：`/agent` 的代理只在开发和 E2E 时生效，生产构建里面板固定显示“调查助手未启动”。要真部署需要另行设计（P10 的范围）。
- **只有两种可采纳原因**（第 4.1 节）。其余原因只能照建议线下处理；`WEBHOOK_LOST` 的补投走 P6 的 catch-up，不走采纳。接受差异的接口没有“操作人”字段，所以手续费差异的采纳表单没有操作人，只有可编辑的原因。
- **预填的备注会带进解释文字**：解释可能含来自银行 memo 的注入文本；前端只当纯文本显示，人可见、可编辑，且只落在备注字段，但确实会被带进纠错记录。
- **MCP 只支持旧式握手和 stdio**：不支持 2026-07-28 的无状态模式、不支持 HTTP 传输、不支持 JSON-RPC 批量；没有 resources、prompts、sampling；每个进程最多 500 次工具调用。
- **E2E 的小毛刺**：测试里用 `route.abort()` 模拟客户端中途断开时，调查服务会在 stderr 打一次 `ConnectionAbortedError` 回溯。这是客户端中途断开的正常表现，不影响结果。
- **E2E 对本机端口敏感**：默认占用 8080、8090、8098、5173；5173 被占时设 `E2E_VITE_PORT`。调查服务在 8098 和 8097 是两个不同的端口（E2E 用前者，手动和开发代理默认用后者）。
- **没有留下代码里的 `TODO`／`FIXME`**；没有新增迁移，没有改动主应用生产代码。
