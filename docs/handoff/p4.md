# P4 验收清单

2026-10-25。P4 = 受限纠错：撤销误记的请款、修正未结算支付的金额（冲销＋重记，样例 E）、待查收款退还、拆分到账归位、银行冲突证据恢复、HELD 批次运营重核。范围见 [phases.md](../design/phases.md)，设计正本是 [ADR-0011 的 2026-10-25 补充](../adr/0011-restricted-correction.md)。

做法同 P3：Claude Code 先定纠错类型（ADR 补充，新增 AC-6.10～6.14），再拆成 10 个小任务（T01–T08，审查中插入 T02b、T05b）；Codex 在本机实现、只跑相关测试、本地提交；本机独立跑一遍全量 verify 全绿才推到 `p4`；Claude 在云端看 diff、独立重跑。每个提交正文带 `Task: Txx`。Codex 停下提问 1 次（T03：能否改 ingestion 内部类、Context7 不可用时查官方文档，都答“可以”）。

本阶段起落实了两条提速改进：Codex 不再跑全量测试（只跑编译、Spotless、本任务相关测试），全量 verify 只由本机执行者跑一次；提问轮工作区干净就跳过测试，等回答每 2 分钟查一次。效果：每个任务从 Codex 开始到推送大约 35–55 分钟，其中全量 verify 只占一次（约 33–36 分钟）；10 个任务在约 8.5 小时内做完，中间没有停摆。

## 4. 值得看一眼的地方

1. **一个新迁移** V20：`ledger.correction`、`ledger.correction_target`（只追加，改删清空由触发器拒绝；readonly 只读视图）；补了 `journal_entry.correction_id`、`recon.issue.resolution_correction_id` 两个外键。**提交时的延迟约束触发器**在数据库层保证：每个 REVERSAL 与原分录逐条镜像（按多重集比较）、每个冲销目标恰有一个对应 REVERSAL、每次纠错至少一个分录、每次最多一个 CORRECTION、归位目标只能是 `UNAPPLIED_CASH_RECEIVED`、REVERSAL 不能被冲销。已提交的迁移没有改动。
2. **扩权**：`app` 新增 `core.payment` 的 UPDATE(`amount`, `expected_fee`)，只用于改金额纠错；银行行新增 `APPLIED`/`RETURNED`/`RETURN_POSTED` 三种状态。
3. **新模块** `corrections`（依赖 ledger、payments、settlement、reconciliation，不被反向依赖）。账本新增 `Ledger.recordCorrection`：冲销行由账本自己从原分录生成，调用方不能提交。`EntryRequest` 仍拒绝 REVERSAL/CORRECTION。
4. **HELD 重核**抽成 settlement 的公开入口，P2 的 UNKNOWN_PAYMENT 自动重核也改走它（`ingestion/internal/PayoutProcessing.java` 这处改动是我答应的），行为不变。
5. **对账规则版本**：BANK/AGING 升为 `p4-v2`（PROCESSOR 不变）。对账只认 `recorded_at < evidence_as_of` 的纠错，所以按旧时点重跑的报告不变。
6. 纠错接口有开关 `ledgerlab.corrections.enabled`（默认开），P7 的公开演示配置关掉它。
7. CI 冒烟任务改为 smoke-p2 之后跑 smoke-p4（smoke-p4 已包含 smoke-p3 的全部检查）。

## 5. 夜里替你定下、可以推翻的取舍

设计层面（都在 ADR-0011 补充里，有理由）：

- 纠错只有四种：`VOID_CAPTURE`、`RESTATE_CAPTURE_AMOUNT`、`APPLY_UNAPPLIED_CASH`、`RESTORE_FAILED_PAYOUT`。没有“任意冲销某分录”的入口。
- **待查收款归位不冲销原入账**：钱是真到了、只是归属不明，所以只记一个 CORRECTION（借 待查收款 / 贷 结算在途），不碰银行现金。原 ADR 写的“一个 REVERSAL 加零或一个 CORRECTION”因此放宽成“形状由类型决定”。
- **待查收款退还不是纠错**：银行出账行明确引用那笔入账流水、金额相等，就自动记 `UNAPPLIED_CASH_RETURNED`；不支持部分退还。
- 撤销要求支付没有任何有效退款（`PAYMENT_HAS_REFUNDS`）；改金额不能低于已退金额（`AMOUNT_BELOW_REFUNDED`），剩余可退额度立即按新金额算。
- 改金额后批次仍对不上：纠错照样提交，批次保持 HELD、差异保持 OPEN。
- 撤销后处理方又把这笔支付结算进批次：批次 `HELD(PAYMENT_STATE_CONFLICT)`，P4 不支持恢复 `VOIDED`，留给人工。
- 手续费差异不纠错（按处理方实际值结算，运营 ACCEPTED）；提现相关冲突留到 P5。
- 没有幂等键：重复提交靠自然约束返回 409，并带上已有的纠错号。

实现层面（Codex 定的，我审查后接受）：

- 运营重核仍不通过时返回 200，带最新状态和原因（不是 409）。
- 银行退还关闭差异时历史原因沿用 `EXPLAINED`，状态为 `RESOLVED`，`resolution_correction_id` 为空（没有纠错号）。
- 纠错页面只读，没有提交表单；纠错只走 API。
