## 2. 自己验收（三条命令，前提是 JDK 25、Node 24、Docker 在运行）

```sh
./mvnw verify                             # 主应用：532 个测试，全部跑在真 PostgreSQL 上，含 Spotless、Error Prone、NullAway、Modulith、JaCoCo
./mvnw -f simulator/pom.xml verify        # 模拟器：25 个测试
cd frontend && npm ci && npm run check && npm run test:e2e   # 前端单测 12 个 + Playwright 3 个
```

想看页面：`npm run test:e2e` 会自己起后端（Testcontainers）和前端；也可以用 `./mvnw spring-boot:test-run` 起后端、`npm run dev` 起前端，再按 `frontend/e2e/payments.spec.ts` 里的方式投递签名的事件。

可选：`./mvnw -Pmodel test -Dtest=PaymentModelProperties` 跑 1000 条随机序列（本机约 7 分钟），报告在 `target/model-report.md`。

## 5. 过程中定下的取舍

都按设计文档推导，记在对应的设计文档里；这里汇总，方便你推翻。

- **验签自己写，不引入 stripe-java。** SDK 只拒绝过旧的时间戳，未来时间本来就要自己查；SDK 等 P3 需要出站调用时再加。新增的运行时依赖只有 `spring-boot-starter-webmvc`（HTTP 入口必需）。
- **签名有效但 JSON 不合法 → 400，不入库。**
- **准入检查的优先级**：livemode > 金额范围 > 币种 > 是否全额请款，只报第一个不满足的。livemode 开 `LIVEMODE_EVENT` 差异，其余三种开 `UNSUPPORTED_EVENT`。
- **P1 的事件类型分流**：`charge.succeeded` 处理；`charge.dispute.*` → `REJECTED/UNSUPPORTED_TYPE` 并开差异；其他所有类型（包括 refund.*、payout.*）→ `IGNORED`，P2、P3 实现时再移出。
- **重试耗尽的事件（`DEAD`）只记状态、不开差异**，留给 P2 的老化检查。
- **worker 抢占用 `FOR NO KEY UPDATE SKIP LOCKED`（Codex 实测发现）**：支付表指向 inbox 的外键会在 inbox 行上加 `KEY SHARE` 锁，用 `FOR UPDATE SKIP LOCKED` 的话，旧 worker 还没结束时新 worker 永远抢不到，租约过期也接管不了。有回归测试证明这一点。
- **差异识别键 (类别, subject_type, subject_id)**；入站差异的 subject 是事件号。关闭后再次出现怎么处理，按 P2 开工前置第 ③ 条重新设计。
- **投递记录表 `io.webhook_delivery`**：同内容重投在 inbox 里不留痕（AC-2.3 要求行数不变），但 AC-1.14 要显示三次投递，所以另记一张只追加的表。`readonly` 通过 `core.v_payment_delivery` 视图只能看到摘要，看不到原文，`io` 对它仍不可见。
- **模拟器是独立的 Maven 项目 `simulator/`**，不和主应用共享任何代码，避免模拟器和被测系统共用同一个错误（ADR-0013）。chaos relay 的扣留最长 240 秒，超时原样转发，保证签名不过期。
- **E2E 后端用 `spring-boot:test-run` + Testcontainers**，不依赖 Docker Compose 和 `.env`，CI 和本机一样跑。
- **审查打回过的一处**：`core.payment.received_at` 起初记的是处理时刻，已改为证据收到的时刻（inbox 的 `received_at`）。

## 6. 遗留问题

1. **模拟器的时钟没有 HTTP 控制接口。** 模拟时钟默认冻结，所以单独运行模拟器时，relay 的 `DELAY` 和扣留超时不会触发；目前只在进程内测试里能用。P2 做联调演示前补 `POST /sim/clock/advance`。
2. **还没有“fake Stripe → relay → 主应用”的跨进程联调测试。** 两边各自用签名和独立校验函数测过协议，主应用的 E2E 用测试里签名的请求。P2 加对账时一起补一个 compose 起三个进程的冒烟测试。
3. **只读数据源没有连接池**，`core.v_payment_delivery` 每次查询都解析事件 JSON 找 charge 编号。P1 数据量下没有问题；P7 做性能基线前改成连接池，并把 charge 编号存成列。
4. **INV-6、7、11 在 P1 没有对应动作**，模型测试报告里写了“不适用”，分别在 P3、P5 扩展。
5. **审计事务的隔离级别没有被测试观察到**（P1a 遗留的 PIT 存活变异）：要等有并发写入的模型动作时补一个“审计期间有人记账也不报假差异”的测试。
6. **Claude 的 Stop hook 有两个问题**：`.claude/hooks/spotless-on-stop.mjs` 在 Windows 上找不到 `mvnw.cmd`（要用绝对路径）；而且它会在 Codex 正在改文件时对工作区跑 `spotless:apply`，和“同一时间只有一方改文件”冲突。这次 Codex 自己跑了 Spotless，没有造成问题。建议修 hook：用绝对路径，并在 Codex 运行期间跳过。
7. **本地只读 MCP（DBHub）**仍需先 `docker compose up -d` 并设置 `LEDGERLAB_READONLY_PASSWORD`（P1a 遗留）。
