## 4. 值得看一眼的地方

1. **报告的口径**：数字只来自公开 HTTP 接口、Stripe 只读列表和已保存的验收结果。`stripe events resend` 总数把补投脚本、验收的重复投递、单事件探测、监听中断后的恢复四类都算进去；任何列表被接口上限截断时报告直接失败，不输出不完整的数字。
2. **对账发现不是缺陷**：27 条 `FEE_MISMATCH` 是因为这一批大多是美国测试卡（`pm_card_bypassPending`），Stripe 实际手续费比我们的国内公式多；批次净额与 Stripe 的 payout 金额相等。1 条 `PAYMENT_NOT_SETTLED` 是 T01 探测支付，还没进任何 payout。真实对账如实报告这类差异。
3. **fake 没改**：真实 Stripe 的退款多发一条 `refund.updated`，`payout.created` 时已经是 `in_transit`＋`completed`；fake 仍是旧行为。改它会动 P3、P5 既有测试的事件序列，所以只写进已知差异，并在契约测试里显式断言了这些差异。
4. **夹具以 LF 写出**：Windows 上 Python 默认写 CRLF，会让两份副本和 Git 的归一化对不上；`write_json` 现在固定 LF。
5. **对账的 cutoff**：接口只接受多伦多零点，所以 AC-8.9 用当前多伦多日的零点，不是任务说明里的“当前整点”（T07 已记）。

## 5. 需要你做的事

- 无必须项。`stripe login` 之前已做过，登录状态保存在你的电脑上。
- 可选：审核后决定要不要为 S3（余额不足时退款 pending）专门构造场景。测试模式下我没能让它出现，若要录，需要先把可用余额耗尽再发起退款，会多创建几笔测试支付和退款。
- **日期提醒**：补投脚本拒绝超过 30 天的窗口（Stripe 事件只保留 30 天）。当前 run 的窗口起点是 2026-10-20，所以 **2026-11-19 之后** 直接跑 `catchup.sh` 会报窗口超限，需要加 `--window-start` 取较新的时刻（最早的事件也已不可补投）。暂停文档里写的 12-02 是按最早事件算的，对默认窗口并不准确。

## 6. 已知限制

- **测试模式下 webhook 和结算明细同源**：事件、balance transactions、payout 都来自 Stripe 同一套测试数据，不像真实环境里处理方通知和银行/批次文件互相独立。对账里的“独立证据”独立性弱于真实场景；银行侧仍是我们自己的模拟银行。
- **评测数字只在模拟器模式报**：P8 的调查 Agent 评测要求故障已知、可重放，真实沙箱做不到；真实沙箱只产出运行报告，不产出评测数字。
- **payout 时间不可控**：首个自动 payout 在最后一笔 charge 之后约 71.6 小时才出现，之后的节奏没观察到。所以只有 1 笔 payout（27 笔支付）；多笔 payout、payout 失败（需要专用测试银行账号）没有真实验证。明细只有一页（28 行），真实多页未录到。
- **退款 pending 未复现**：官方文档说余额不足时卡退款会 pending，测试模式下我们的两笔都是 `succeeded`，S3 夹具缺失，pending 路径只由 fake 和单测覆盖。
- **费率**：美国测试卡的 Stripe 实际手续费比国内公式多；国内卡 `30 + round(2.9%)` 只验证了单笔金额，没覆盖所有舍入边界。
- **本地接口上限**：支付最近 100 笔、批次与差异列表各 100 条；超过时报告会失败而不是少算，需要给接口加分页。
- **流量**：28 笔支付、2 笔退款、1 笔 payout 是沙箱里的全部，不代表吞吐。性能基线在 P7。
