# P3 验收清单

2026-10-25。P3 = 退款：状态机、额度与并发、资金门槛与等待队列、处理方可用余额、出站命令（先查后发、完整分页查询、`first_sent_at`）、API 幂等与业务编号，外加 P2 遗留的 inbox 状态历史＋`EVENT_PARKED_AGED` 和批次不支持行的专门差异类别。范围见 [phases.md](../design/phases.md)。退款仍对 fake Stripe，真实 Stripe 测试模式留到 P6。

做法同 P2：Claude Code 把 P3 拆成 15 个小任务（T01–T14，审查中插入 T04b），每个任务写明范围、AC、测试场景和不许碰的文件；Codex 在本机实现、跑相关测试、本地提交；本机再独立跑一遍 verify 全绿才推到 `p3`；Claude 在云端看 diff、再独立重跑后才放行下一个。每个提交正文带 `Task: Txx`。Codex 停下提问 3 次（T03 一次、T04 两次），问题和回答按任务留档（不在本仓库主线里）。

## 1. 合并方式

一个 PR：`p3` → `main`，基于当前 `main`（`ee72b93`），不叠加。合并这一个就完成 P3。

## 2. 自己验收（前提：JDK 25、Node 24、Docker 在运行）

```sh
./mvnw verify                              # 主应用：1366 个测试，全部跑在真 PostgreSQL 上
./mvnw -f simulator/pom.xml verify         # 模拟器：122 个测试
cd frontend && npm ci && npm run check && npm run test:e2e   # 前端单测 21 个；Playwright 共 10 个
sh scripts/smoke-p3.sh                     # 三进程冒烟：fake Stripe → relay → 主应用，含退款
sh scripts/smoke-p2.sh                     # P2 冒烟仍然通过
```

两个冒烟脚本共用 `scripts/smoke-common.sh`（一次性 compose 项目名、只读公开的假凭证 `compose.smoke.env`、不读 `.env`、结束删容器和卷），检查逻辑在 `scripts/smoke/*.py`（原 smoke-p2.sh 就依赖 Python 3.9+，没加新工具）。smoke-p3 成功时依次输出 PASS：退款命令真的发到 fake Stripe、`refund.created` 经 relay 重复投递只记一次执行、同键重放结果一致；B2 批次含退款行（毛额 5000、手续费 175、退款 −2000）；处理方余额不足时 R2 保持 `SUBMITTED`，处理后 `refund.updated` 到达变 `SUCCEEDED`；最后三段对账 0 发现、0 差异、账本不变。证据在 `target/smoke-p3/`。

可选：`./mvnw -Pmodel test -Dtest=PaymentModelProperties` 跑随机序列（现已加入退款受理、取消、放行、提交、超时、查询、各类证据），报告在 `target/model-report.md`；`RefundStatefulProperties` 在 CI 的 model 任务里一起跑。

## 4. 值得看一眼的地方

1. **新增迁移** V13–V19（主应用）和 V5（模拟器），每张新表都写了 `migrator`/`app`/`readonly` 授权，readonly 只能读视图（出站尝试走脱敏视图 `core.v_refund_attempt_summary`，只含标识、时间、结果码）；已提交的迁移没有改动。
2. **新模块** `refunds`、`outbound`。`ingestion` 允许依赖这两个，`settlement` 允许依赖 `refunds`（Modulith 边界测试通过；是新增依赖，不是放宽已有规则）。
3. **公开接口只增不改**：`Ledger.balance(Account)`（退款队列读 2102 走账本接口，不直接读 `ledger` schema）、持锁断言、`PaymentRefunds`（供退款锁定支付并查额度）。
4. 出站命令按 ADR-0008 用 `FOR UPDATE SKIP LOCKED` 抢占（任务说明原写法与 ADR 冲突，按 ADR 改）；查询也计入调用次数，达上限停止自动重试。
5. `io.idempotency_record`（API 幂等缓存）是唯一允许 app DELETE 的新表，用于过期清理；它不是账本数据。
6. 对账规则版本升为 `processor-v2`、`p3-v2`。
7. CI 的 model 任务加跑 `RefundStatefulProperties`；CI 的冒烟任务在 smoke-p2 之后加跑 smoke-p3（只能在 GitHub 上验证；本机和云端都跑过脚本本身）。
8. E2E 的“响应丢失”用测试启动器里的 loopback 代理注入，只在 `src/test`，生产产物不含这个入口。

## 5. 夜里替你定下、可以推翻的取舍

- readonly 不直接读新底表，只读视图（任务说明和 ADR-0014 冲突时按 ADR）。
- API 幂等记录在 INSERT 时就写好 `initial_result`、`expires_at`，之后不 UPDATE；4xx 结果不留任何行。
- 业务编号重放时返回受理当时的结果（`initial_result`），不返回当前状态。
- fake Stripe 退款幂等键至少保留 24 小时；我方 20 小时后先做完整分页查询再决定是否重发。
- 查询返回 404、或金额/charge/metadata 对不上时，保持 `UNKNOWN`，不自动判失败。
- 未知退款的 webhook 不走 `PARKED`，记 `UNKNOWN_REFUND`。
- P2 已有的 HELD 批次不自动重核；非零退款手续费计入批次总费用。
- 退款老化：等待资金、未执行按 `evidence_as_of` 起算；已执行但结算单缺行按 `cutoff_at`。
- 页面退款金额输入要求两位小数，按整数分转换。
