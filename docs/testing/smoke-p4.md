# P4 HTTP 冒烟（T08）

仓库根目录运行 `sh scripts/smoke-p4.sh`（Windows 用 Git Bash）。需要 JDK 25、Docker
Compose v2、Python 3.9+，与 P3 相同。脚本先完整跑 P3（包含 P2），清理后再启动另一个
全新 Compose 项目跑 P4。只加载公开的 `compose.smoke.env`，不读取 `.env`、不联系真实
Stripe；P4 的动作与断言全部走 HTTP，不读写数据库。

CI 保留原有独立 P2 作业步骤，以 P4 入口覆盖原有 P3 步骤，因此 P3 的退款、重复投递、
pending 执行和 ALL 对账断言全部保留。P3 与 P4 使用两个空库，P4 可直接核对样例 E 的
绝对余额；代价是多一次构建和启动。P3 的证据仍在 `target/smoke-p3/`，P4 的请求、响应、
银行 CSV、对账报告与服务日志在 `target/smoke-p4/`。CI 上传 P2/P3/P4 三个目录，保留七天。
各项目无论成功或失败都执行 `down -v`，不触碰开发环境的容器和卷。

P4 覆盖：

- AC-1.4d、AC-6.5：样例 E，原支付 4500，独立处理方明细 5400／手续费 187，B6
  `HELD(AMOUNT_MISMATCH)`；带差异、结算单行和原事件证据提交金额纠错，核对精确镜像
  REVERSAL 与 CORRECTION、原分录不变、支付金额及退款额度同步、B6 自动 `CONFIRMED`、
  差异 `RESOLVED`、在途和可用各 5213。
- AC-6.3：撤销另一笔未结算的 10000 支付，只生成 REVERSAL，支付 `VOIDED`，应收和
  待结算回到零，其他账户不变。它在所有 payout 创建后生成，避免被后续批次结算。
- AC-5.6、AC-6.9：模拟银行重复支付 9680，一笔精确匹配，另一笔进入待查；导入次日的
  等额出账后，原流水 `RETURNED`、出账 `RETURN_POSTED`，产生业务分录
  `UNAPPLIED_CASH_RETURNED`，差异关闭且解释引用出账流水，不产生纠错。
- AC-6.10：模拟银行的 SPLIT 固定等分，故用 4840＋4840（专项 AC 测试的 5000＋4680
  不变）。两个入账先成为待查并各开金额差异；运营归位后均 `APPLIED`，批次 `BANKED`，
  只有借 2105／贷 1102 的 CORRECTION，现金不变，两条差异关联本次纠错关闭。
- AC-5.8：最后持久化一次 ALL，PROCESSOR／BANK／AGING 均 FINISHED、零 findings，
  四条故意产生的差异全部保持 RESOLVED，没有豁免的 OPEN 差异。检查运行输入包含最终
  处理方快照、银行入账与退还文件，报告可读取，业务对象和账本不被对账修改。

样例 E 使用模拟器既有 payout `amount`、`omit_transaction` 和 `extra_line` 故障接口，
让外部结算明细与原请款不一致；不改生产解析器、不直接改账。模拟器没有银行退还出账
控制接口，因此脚本构造独立合成 CSV，经正式 `/api/bank-statements` 导入。退还金额、
期初 34253 和期末 24573 均为脚本手算常量，不由本地账本反推；只从外部流水取得引用编号。
银行先一次导入样例 E、重复打款和拆分到账的入账，再依次退还、归位，每步核对全部八个账户。

P4 使用 2026-10-19 的处理方业务日、10-20 的入账、10-21 的退还，cutoff 为多伦多
10-22 零点；证据时点取全部写入之后，并按应用 Clock 等待原有 60 秒宽限。整个入口的
主机时间下限仍由 P3 决定：`2026-10-24T04:00:00Z`。最终 P4 现金和商户可用均为 24573，
其余账户均为零。没有新增依赖、迁移或生产故障开关。
