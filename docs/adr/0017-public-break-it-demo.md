# ADR-0017 公开的“来搞坏它”演示页

状态：已采纳（2026-10-21，P0）。来源：交接说明第 14 节第 3 项。

## 背景
项目没有真实用户。一个任何人都能动手“搞坏”的公开沙箱，是替代“真实用户”的直观证据，也是技术文章的素材。

## 决定
- **沙箱用模拟器模式**（fake Stripe ＋ 模拟银行）：确定、免费、不受 Stripe 速率限制，不暴露任何密钥。页面另有一块只读面板，展示最近一次真实 Stripe 测试模式运行的报告（ADR-0016）。
- **一个共享沙箱，定时重置**（每天一次，另可在异常时手动重置）。访客看到的是同一个账本，这样“别人刚才的并发退款”也能看到。
- **访客能做的动作是白名单**，每个动作一个按钮：发一笔支付；重放上一条 webhook；把批次事件抢在支付事件之前投递；并发两笔退款；提交后丢响应再重试；让银行执行后丢回执；在命令处理中杀掉 worker；导入一份带差异的结算单。没有任意请求、任意 SQL、纠错和运营接口。
- **实时证据**：每个动作之后服务端跑 INV-1～INV-11，把结果和事件时间线通过 SSE 推到页面；页面同时显示“被吸收的重复投递”“被拒绝的超额退款”等计数。
- **服务端约束**：演示动作只在 `demo` 配置下注册；按 IP 和全站两级限流；故障注入钩子只在 `demo` 和测试配置里编译进来、生产配置里不存在；Agent 和调查接口访问不到这些动作。
- **统计**：只记聚合访问量和动作次数，不用跟踪 cookie，不收集个人信息。对外只写实测的访问量，不写成用户数。

## 备选
- 每个访客一个独立沙箱：互不干扰，但每人要一套库或 schema，成本和复杂度高；单商户模型下共享沙箱已经够演示。
- 页面直接驱动真实 Stripe：更“真”，但受速率限制、可能被滥用，还要把一部分 Stripe 能力暴露给公网。只做只读报告面板。

## 后果
- 系统要在公网写流量下保持正确，这本身就是测试；部署和限流成为 P7 的验收内容。
- 文章（交接说明第 14 节第 4 项）以这个页面和背后的测试为素材。
