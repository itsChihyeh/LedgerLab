# ADR-0001 结算在途与批次净额

状态：已采纳（2026-10-21，P0）。来源：复核 S2。

## 背景
立项稿把“处理方确认结算”直接记成银行现金，并把退款记成结算后再单独扣现金。真实处理方（Stripe payout 对账报表、Adyen settlement details report）按批次净额打款，退款和手续费都在批次里抵扣；“处理方说已结算”和“钱进了我们的银行账户”是两件事，中间可能隔几天，也可能失败。

## 决定
- 新增资产账户 `settlement_in_transit`。批次确认时记入在途，银行流水按批次号精确匹配到入账行时才转成 `bank_cash`。
- 批次 = 处理方的一笔打款（Stripe payout）。净额 = 支付毛额 − 手续费 − 本批扣掉的已执行退款 + 退回的失败打款。退款不再单独动现金。
- 处理方余额 ≤ 0 时不产生批次；负数留在 `processor_receivable` 上，由下一个批次扣回（与 Stripe 的行为一致，2026-10-21 随 ADR-0016 修订，原先的“负净额结转批次”取消）。
- 批次记账前逐项核对批次行与本地记录，零容差；对不上就 `HELD`。

## 备选
- 批次确认即记现金：简单，但让“已确认未到账”的钱可以被提走，三方对账也失去意义。
- 处理方对负净额直接扣我们的银行账户：更接近部分真实处理方，但会让银行现金可能为负，首版不做。

## 后果
多一个过渡账户和一种证据（银行流水），对账从两方变成三方；提现门槛要看“没被占用的现金”（ADR-0005）。

## 补充（2026-10-21，开工前审查）
- 删去“处理方余额 ≤ 0 时不产生批次……与 Stripe 的行为一致”：这不是 Stripe 的行为。Stripe 的卡退款只用可用余额，不够时 pending；余额真的变负时，Stripe 会建一笔从银行账户扣款的负 payout。
- 首版只处理净额 > 0 的标准自动 payout；负 payout 和其他不支持的 payout 在入口隔离（批次 `HELD(UNSUPPORTED_PAYOUT)`，开差异），模拟银行不把它当收入。这是本项目的范围限制，不是对 Stripe 的描述。
- 批次在 payout 明细就绪（`reconciliation_status=completed`）后才拉取核对，见 design/stripe-integration.md 第 2 节。
