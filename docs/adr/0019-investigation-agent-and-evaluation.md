# ADR-0019 调查 Agent：可替换模型接口、回放评测集与规则基线

状态：已采纳（P8，2026-11-06）。来源：立项说明第 6 节；P8 开工设计（Claude 规划，用户 2026-11-05 定“先接口和本地替身，外部 API 最后由用户接”）。设计正本：[investigation-agent.md](../design/investigation-agent.md)。

## 背景
对账差异的类别由确定性代码给出，但类别不等于原因（例如 `UNMATCHED_BANK_LINE` 可能是银行重复入账、币种标签错或来历不明的来款）。要让一个大模型调查原因，同时守住三件事：它不能改任何东西；它的结论能被检查（引用的记录真实存在）；它的“好”是测出来的，而不是演示里挑出来的。外部模型要花钱、要用户账号，P8 的大部分工作又必须先在本地跑通。

## 决定
1. Agent 是独立 Python 进程（`agent/`，uv，运行时只用标准库），只通过 investigation 的只读 HTTP 接口取数；工具层把模型选的工具和参数拼成固定模板的 GET，路由清单 `routes.json` 由 Java 测试在服务端逐条验证为 readonly 只读接口。
2. 模型接口 `ModelClient.complete(request) -> response` 与厂商无关；先实现 `ScriptedModel`（单测）和 `StubModel`（本地替身＝规则基线经同一个 Agent 循环输出），外部模型适配器最后在用户批准后加，SDK 作为可选依赖。
3. 评测集由生成器在一次性栈上注入已知故障产生，标签记生成器自己注入了什么；随后爬取每条差异可达的记录存成快照，评测默认在**快照回放**模式下跑。开发集、测试集用不同种子生成后冻结进仓库。
4. 指标固定为：原因准确率、编造引用数、引用支持率、拒答召回与误拒、提示注入照做数、工具调用与延迟、token 与费用。硬线是编造引用 = 0、提示注入照做 = 0；大模型相对规则基线的成绩如实报告，不设必须超过的门槛。
5. 提示词、SOP、规则只看开发集调整；测试集每个配置只跑一次用于报告。

## 备选
- **让 Agent 直接用 readonly 角色连数据库、写 SQL**：违反 ADR-0014“没有任意 SQL”；被注入后可以读到与问题无关的数据、拼出跨时点的状态。不选。
- **用 Java 写 Agent、放进主应用**：可以复用 investigation 代码，但模型调用、评测和提示词迭代都和资金进程绑在一起，崩溃或依赖问题会波及主应用；立项时已定 Python 独立进程。不选。
- **评测只在线跑（每次起栈）**：最真实，但每次几分钟、结果随时间推进变化，不能把评测集提交进仓库复现。保留为可选模式，默认回放。
- **用 LLM 当裁判打分解释质量**：主观、要花钱、可被同一类错误蒙混。首版只用可自动核对的指标；解释质量在报告里人工抽查若干条并注明。

## 后果
- 回放模式下，爬取范围之外的记录对 Agent 不可见；报告必须写明这个限制。
- 替身分数等于规则基线是设计使然，只证明管线不丢信息，不证明任何“AI 能力”；报告和简历都不得把替身分数当成模型成绩。
- 新增一个只读后端接口（按 reference 查银行流水）；其余工具复用已有接口。
- 对应 AC-10.1～AC-10.10；测试见 `docs/handoff/p8.md`。
