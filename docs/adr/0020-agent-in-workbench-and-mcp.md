# ADR-0020 调查 Agent 进工作台：结论存在 Agent 一侧，采纳走已有写接口；同一组只读工具做成 MCP 服务

状态：已采纳（P9，2026-11-06）。来源：P8 收尾时提出的 P9 范围（用户要求阶段依次推进）。设计正本：[agent-workbench-and-mcp.md](../design/agent-workbench-and-mcp.md)。

## 背景
P8 的 Agent 只是一个命令行：运营在工作台上看不到它的结论，也没法把结论变成处置。把它接进工作台时要守住 P8 的底线：Agent 不能写任何东西；结论只是建议，任何改动都要人确认并经过已有的校验；主应用（资金进程）不因为 Agent 多出依赖或失败模式。同一组只读工具还应该能被别的 Agent 客户端复用，而不是每个客户端各写一套取数代码。

## 决定
1. Agent 以一个本机调查服务（Python 标准库 `http.server`，只听回环地址）的形式提供给前端；主应用不加表、不加路由、不调用 Python。调查结论存在调查服务自己的只追加 JSONL 文件里。
2. “采纳”是前端里的一张封闭映射表：只有 `BANK_SPLIT_DEPOSIT`（→ 已有的 `APPLY_UNAPPLIED_CASH` 纠错）和 `PROCESSOR_FEE_DIFFERS`（→ 已有的“接受差异”）两种原因能采纳；采纳只展开预填表单，人填操作人并点提交后才发一次 POST 到已有接口。引用里有核验不通过的记录时不允许采纳。
3. 追溯靠已有记录：纠错备注或差异处置说明以 `采纳调查 inv_…` 开头，对应调查服务里同号的完整记录。
4. MCP 服务是核心包外的独立包（不改变评测的代码指纹），用标准库实现 stdio JSON-RPC，工具定义与校验全部复用 P8 工具层，只暴露只读工具，不提供调查、资源或提示词；实现初始化式握手（2025-11-25／06-18／03-26），不实现 2026-07-28 的无状态模式。
5. 服务和 MCP 都只用规则基线或本地替身；外部模型仍等用户批准（AC-10.10），不接进服务。

## 备选
- **主应用加 `agent_run` 表，由主应用保存结论**：结论和处置能在一个库里关联，但要么 Agent 获得写主应用的入口（违背零写权限），要么前端把模型输出转交给主应用落库（资金进程开始存储不可信文本，多一个迁移和三角色授权）。追溯用备注里的调查号已经够；不选。
- **主应用调用 Python 子进程或 HTTP 调查服务**：主应用多一个运行时依赖和失败模式，调查慢会占用主应用线程。不选。
- **采纳后由 Agent 或调查服务直接调用纠错接口**：等于给 Agent 写权限，被注入时后果不可控。不选。
- **用官方 `mcp` Python SDK**：协议细节更省心，但是新运行时依赖（铁律 5），而 P9 需要的只是 stdio 上的四个方法。不选；以后协议升级到必须用 SDK 时再问。
- **采纳覆盖所有建议动作**：其余动作（等下一份流水、找银行或处理方、补投事件）在系统里没有对应的写操作，硬做成按钮只会造出假的“处理完成”。不选。

## 后果
- 调查服务没启动时面板只提示未启动，工作台其余功能不受影响；生产构建默认就是这种状态。
- 调查记录随本机文件走，不进备份、不进账本；删掉文件只丢调查历史，不丢处置记录。
- 采纳的正确性完全由后端已有校验保证；前端映射错了最多是一次被拒的请求。
- 只有两种原因能采纳，其余结论只能看、不能一键处理；这是有意的。
- 对应 AC-11.1～AC-11.8；测试见 `docs/handoff/p9.md`。
