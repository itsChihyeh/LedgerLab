# ADR-0013 模块化单体；处理方和银行模拟器分开

状态：已采纳（P0）。来源：立项 Q2、复核 I6。

## 决定
- 主应用是一个 Spring Boot 模块化单体：`ingestion`、`payments`（支付/退款）、`payouts`、`ledger`、`settlement`、`reconciliation`、`investigation`（只读查询），边界由 Spring Modulith verify 检查。
- 模拟器是同仓库里单独启动的进程，内部分成 `processor` 和 `bank` 两部分，各有自己的 schema 和状态，只通过它们对外的接口（webhook、文件、银行 API、银行流水）互相影响。主应用看不到模拟器的库。
- 参考模型（模型测试用）是独立的小段纯 Java 代码，不复用业务代码。
- 手算样例（money-model 第 6 节）是第三份独立真值，测试里逐步对照。

## 理由
模拟器、参考模型和评分器如果共享同一个错误，会一起通过测试；三份真值来源互相独立，才能互相检验。

## 后果
多维护一个进程；换来的是“外部世界真的会失败、重试、推进时间”，这是和 ReconRiver 等竞争者的区别。

## 补充
- 银行流水由模拟银行**实际执行**的记录产生，不能直接复制处理方“打算汇多少”；处理方可以说打款 X，银行可以只到账 Y 或到两次。
- 生产查询（主应用、调查接口）看不到 `sim_truth`。
- 关键资金写入（记账、额度、命令落库）用显式同步调用，不为了 Modulith 改成提交后的异步监听器。

## 补充（2026-10-21，随 ADR-0016）
模拟器的处理方部分改为 fake Stripe（说 Stripe 协议子集）；故障注入拆成独立的 chaos relay，模拟器和真实 Stripe 两种模式共用。模拟银行不变。
