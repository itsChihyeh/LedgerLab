# ADR-0021 可观测性：自带结构化日志、独立管理端口上的 Actuator 指标、一条有测试的 Prometheus 告警

状态：已提出（P10，2026-11-07）；第 2、3 条涉及的新依赖等用户批准（铁律 5）。设计正本：[observability.md](../design/observability.md)。

## 背景
到 P9 为止，系统的正确性靠测试和对账证明，但运行时几乎看不见：全仓只有 8 条日志、没有指标、没有告警。真实部署（P7 方案）之前需要回答三个问题：出了事能不能按一个编号把相关日志串起来；入账、出站、对账有没有在卡住；卡住时谁会知道。同时不能破坏已有边界：资金写入路径不变、公开演示站只暴露白名单接口、确定性重建（AC-4.13）不受影响、不引入新基础设施。

## 决定
1. 日志用 Spring Boot 自带的 `logstash` 结构化格式，由环境变量开启；关联靠 MDC 里的固定键（`requestId` 和各业务编号），统一由一个可关闭的上下文工具放入和清除。请求号不用业务 `IdGenerator`。只记固定名字的业务事件，不记请求体、签名头、密钥和自由文本。
2. 指标用 `spring-boot-starter-actuator`＋`micrometer-registry-prometheus`（版本跟 BOM），放在只听 127.0.0.1 的独立管理端口，只暴露 `health` 和 `prometheus`。业务 gauge 每次抓取时经 `readonly` 数据源查库，查询放在拥有数据的模块；标签只用封闭枚举。
3. 告警只有一条：inbox 里已到期事件等待超过 5 分钟、持续 5 分钟。规则写成 Prometheus 规则文件，用 `promtool test rules` 在固定版本的测试容器里验证，并且有一个测试从真实应用的指标把它触发出来。
4. 调查服务（Python）的耗时由它自己用标准库输出 Prometheus 文本，不经主应用。
5. 部署只更新方案和报价；任何云操作、费用和对外发信（告警通知）都等用户决定。

## 备选
- **自写指标端点，不加依赖**：零依赖，但手写格式、没有 JVM／HTTP 自带指标，与行业标准做法不一致；作为用户不同意加依赖时的退路保留在设计第 8 节。
- **业务 gauge 用内存计数，不查库**：便宜，但重启丢失、多实例不准，而且 inbox 和出站命令的真相本来就在表里。查库的代价是每次抓取几条带索引的只读 SQL，可以接受。
- **告警选“未结差异数”**：对账差异是业务现象，有的要等下一份流水才会自动消失，不适合作为叫人的信号。inbox 卡住正常时恒为 0，是资金入账停摆的最早信号。
- **OpenTelemetry／分布式追踪、Loki／ELK、Grafana**：要新基础设施或依赖，单体单实例收益小；留给 P11。
- **Actuator 挂在主端口**：要在演示白名单和 Caddy 里各开口子，暴露面变大；不选。

## 后果
- 默认（不设环境变量）日志格式不变，现有测试输出不受影响；部署和演示站输出 JSON。
- 新增两个 Spring Boot 官方依赖（批准后）和一个只在测试里用的 Prometheus 镜像；ArchUnit／Modulith 边界不变。
- 抓取频率决定了 gauge 查询频率；默认 15 秒一次，对单实例演示库可以忽略。
- 告警通知渠道没有定，本地只能在 Prometheus 页面上看到 firing。
- 对应 AC-12.1～AC-12.9。
