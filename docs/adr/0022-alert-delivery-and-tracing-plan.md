# ADR-0022 告警经 Alertmanager 送到本机接收程序；补三条规则；追踪只写方案

状态：已提出（P11，2026-11-07）；第 2 条用到的 `prom/alertmanager` 镜像等用户批准。设计正本：[alerting-and-tracing.md](../design/alerting-and-tracing.md)。

## 背景
P10 留下一条有测试的告警，但它只在 Prometheus 页面上变红，没人会收到；应用整个挂掉时它反而不会触发（没有数据）；出站命令达到上限、对账运行失败这两种需要人处理的情况没有告警。用户决定项目做完之前不上云，所以送达只能先在本机证明，真实渠道（对外发送）留给用户选。追踪是 P10 明确留给 P11 讨论的项，它需要新依赖、新基础设施和迁移。

## 决定
1. 加三条规则：出站命令达上限（`ticket`）、对账运行失败（`ticket`，靠新的进程内 counter `ledgerlab.recon.runs`，因为失败的运行整笔回滚、库里没有记录）、应用指标抓不到（`page`，补“应用死了其他告警都不响”的盲区）。都用 `promtool test rules` 验证。
2. 送达用 Prometheus 标准的 Alertmanager，按 `severity` 路由，接收方先只有一个本机 webhook 接收程序（Python 标准库，只听 127.0.0.1，写 JSONL）。端到端测试从真实应用触发，经 Prometheus、Alertmanager 到测试里的接收端，验证 firing 和 resolved 都送到。测试用的时间参数可以缩短，但必须由测试证明副本与仓库正本只差时间字段和地址。
3. 真实通知渠道的地址和凭证不进仓库（走 `url_file` 或环境变量），选哪个渠道、是否对外发送由用户决定。
4. 分布式追踪只写方案文档（[tracing.md](../design/tracing.md)），列依赖、迁移、确定性影响和代价，不实现。

## 备选
- **应用自己发通知（不用 Alertmanager）**：少一个组件，但要自己做分组、去重、静默、重复间隔，和行业做法不一致；不选。
- **直接接邮件或聊天软件**：能真的收到，但属于对外发送，需要用户账号和凭证，用户还没选；先做本机接收，渠道是加一个接收方的事。
- **对账失败写库再告警**：失败运行在回滚的事务里，写库要另开事务，改动关键路径；进程内计数加 `increase()` 足够，重启丢计数的代价是可能漏一次 `ticket`，可以接受。
- **现在就实现追踪**：单体单实例收益有限，要新依赖、导出端和迁移（inbox、出站命令表存 trace 上下文），还会碰确定性重建；先写清楚代价让用户决定。

## 后果
- 本机能看到一条告警从真实应用一路送达；部署时换一个接收方即可。
- `observability` profile 多一个 Alertmanager 容器（批准后），内存估算多一行。
- 对账失败计数重启归零；规则用 30 分钟窗口，重启只影响窗口内的告警。
- 对应 AC-13.1～AC-13.8。
