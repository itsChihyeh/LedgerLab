# ADR-0004 并发：悲观行锁与固定加锁顺序

状态：已采纳（P0）。

## 背景
退款要防超退（同一支付的并发退款），退款和提现会争同一个商户余额，批次结算和退款执行会同时改处理方应收。

## 决定
- READ COMMITTED 加 `SELECT … FOR UPDATE`。
- 全局加锁顺序：先业务行（支付 → 退款 → 提现 → 批次，同类按编号升序），再账户行（按账户代码升序）。记账入口自动把涉及的账户排序后加锁（参考 pgledger）。
- 提现门槛读 1101、1103、2102、2104 时一并加锁，防止并发提现各自看到同一份可用现金。
- 写一组“去掉锁会出错”的失败测试：去锁后并发退款超退、并发提现超提，证明锁是必要的。

## 备选
- SERIALIZABLE 加重试：正确，但冲突时整个请求重来，出站命令和幂等记录的交互更复杂。
- 乐观版本号：适合低冲突；商户余额行是天然热点，冲突率高。

## 后果
单商户下所有改余额的操作在 2102 上串行，吞吐受限；k6 基线会报告这个数字，并说明多商户时按商户分片即可。

## 补充（2026-10-21，开工前审查）
- 原决定只规定了**一次记账调用**内的账户顺序，没有规定整笔事务的顺序。批次重处理、退款队列放行、多分录纠错都会在一个事务里多次记账，可能形成死锁（例：事务甲持有支付 P1 和账户 1101 后去锁 P2，事务乙持有 P2 在等 1101）。
- 改为：每个会动钱的事务**第一步**锁 `ledger.funds_lock` 的唯一一行，然后才按“业务行 → 账户”的顺序加锁。单商户下资金写入本来就在 2102 上串行，这把锁不降低吞吐；多商户时按商户一行。
- 提现门槛读取并锁定的账户加上 2105（待查收款），与 money-model 4.2 一致：1101、1103、2102、2104、2105。
